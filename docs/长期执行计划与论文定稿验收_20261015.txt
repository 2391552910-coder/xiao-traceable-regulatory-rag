一 目标与预计时间

完成年报 PDF 与法规文件的导入、解析、切分、索引、双路检索和真实生成，
在冻结评测集上跑完正式对照与消融，完成独立复核、统计、图表、复现材料和小论文定稿。
系统直接检索文档；不把穷尽式公司事实抽取作为运行或论文的必要前置工作。

主排期：2026-10-15 至 2026-11-20，约 5–6 周。
按周一至周五估算共 27 个工作日，含开发、标注准备、运行、复核与写作，并非连续 27 天计算。
预计实验、独立复核和主要分析于 11 月 13 日形成完整版本，论文于 11 月 20 日定稿。
另预留 11 月 23 日至 27 日处理失败重跑、复核延误或投稿版式调整。

以上是计划日期，不是已完成状态。前面的 1–2 个工作日估算对应真实问答先导；
完整论文还需要新评测数据和正式核验，不能沿用仅计算运行时间的收尾估算。

排期前提：
1. 一台 GTX 1660 Ti 6 GiB 主机可稳定使用，Embedding 和 Reranker 使用隔离 CUDA 环境。
2. 生成 API 可访问、配额可用；正式跨模型实验需要至少两个独立模型族的可用服务。
3. 能安排实际复核人员。双人独立复核按真实参与记录验收，AI 辅助不写成真人标注。
4. 先导后登记生成调用预算和人工工作量，再冻结正式规模；不在看最终结果后调整样本。

三 阶段排期与验收

阶段 P1 真实生成先导与可复用运行环境
日期：10 月 15–16 日，2 个工作日。
工作：
1. 使用少量已有原文证据做一次真实 API 请求，先检查认证、模型名称、结构和返回内容。
   不先为密钥连通测试重新编码全库。使用 --real-llm 并记录 generation_mock=false。
2. 将生成器、辅助评估器配置分开；记录真实模型、调用日期、参数、失败和重试。
3. 实现索引保存、加载及批量问题复用。缓存绑定原文件、片段、模型 revision、查询指令、
   精度、切分配置和语料清单哈希；内容变化时失效，不修改历史哈希使旧缓存通过。
4. 在 GPU 新默认配置上建立一次全量索引，保存向量、片段顺序及来源映射。
   预计计算 1–2 小时，实际以记录为准，不能用此前 float32 结果替代。
5. 运行 10–20 个先导问题，检查两路检索、真实回答、引用链接和证据不足状态。
6. 保存当前源码变更清单和快照，准备隔离实验副本；保留所有已有修改与历史结果。
验收 G1：
真实调用有原始响应；运行标记为真实生成；GPU 与精度可核查；第二次查询可复用索引；
缓存篡改或源文件变化会被拒绝；首批问题有来源记录、失败记录和问题清单。
此阶段通过仅说明真实问答和复用链路可用，不作为正式质量结论。

阶段 P2 数据协议与研究问题定稿
日期：10 月 19–23 日，5 个工作日。
工作：
1. 核对最近相关工作，建立与普通混合 RAG、双源检索和引用生成的差异矩阵。
   不把采用 Qwen3 或常规组件组合单独写成原创算法贡献。
2. 冻结研究假设、主指标、基线、证据预算、比较单位及负结果报告方式。
3. 审计正式使用的 39 份年报与法规输入：身份、重复、版本、正文、页码、条款、时间信息。
   只在新清单中登记正式输入，保留旧清单、gold、复核和原文件。
4. 建立问题级评测协议，记录公司、年度、问题族、可回答性、年报支持段、法规依据、
   论断角色和适用条件。关键词候选只是定位辅助，不直接转为 gold。
5. 规划新双源集至少 200 个问题，目标为 40 开发、160 最终测试；按公司和语义问题族隔离。
   原 40 个历史检索开发问题继续保留，不能直接冒充新双源最终测试集。
6. 检查原 D1–D4 范围与实际输入是否相容。年报和法规不足以回答的外部声誉、处罚等问题，
   可作为明确的不可回答场景；不为凑各维度配额补造事实。若需调整原各维度至少 50 题的
   规划，在查看最终测试结果前登记范围、理由及新的分层配额。
7. 根据先导请求实测延迟、token 和费用，登记正式调用预算、并发、重试上限及停止条件。
验收 G2：
形成数据清单、标注规范、问题候选、公司与问题族划分、研究假设和实验配置版本。
所有样本量调整在最终测试前记录，不能按照结果好坏选题。

阶段 P3 独立复核与开发集诊断
日期：10 月 26–30 日，5 个工作日。
工作：
1. 对问题及其双源证据逐项复核，补充候选池外相关段落，记录分歧与未知条件。
2. 将来源是否存在、语义是否支持、法规是否适用分别标注，不能由引用编号有效推断后两项。
3. 在开发集上比较稠密、BM25、融合、重排与切分设置；冻结主配置。
4. 校正评测程序：不同切分共用原文证据坐标；保留所有重复生成；失败不静默填零；
   空引用比例记为不适用，仍评价论断支持；按公司及问题族处理相关性。
5. 完成至少一次小规模正式流程演练，从原始输出复算指标与图表。
6. 冻结正式测试清单、证据标签、代码快照、模型、提示、索引、依赖与哈希。
7. 决定微调是否有必要。默认冻结模型；若没有可靠训练数据与明确开发集诊断，不增加训练。
验收 G3：
评测集和代码有明确版本；主配置仅由开发集选择；最终测试不用于调参；
标注与核验过程可追溯，真实复核人员和 AI 辅助分别登记。
若实际复核人手不足或重要法规适用信息尚未确定，不将本阶段标记为正式冻结通过。

阶段 P4 正式检索与生成实验
日期：11 月 2–6 日，5 个工作日。
工作：
1. 检索主比较：BM25、Qwen Dense、Hybrid、Hybrid 加 Reranker；
   比较统一候选与双语料作用域召回，保持相同文本快照和合理的总候选预算。
2. 生成主比较暂定四组：无检索、混合语料普通 RAG、双源 RAG、双源逐论断引用方法。
   最终组名和实现差异在 G3 前冻结，不能用相同实现换名称制造不同方法。
3. 固定总上下文 token 预算、生成模型和参数，避免将两路各 5 段与单路 5 段直接比较。
4. 每个问题、每种模式生成 3 次，保留 repeat_id、完整响应、引用、延迟、token、错误与重试。
5. 以 160 个测试问题、4 组、3 次重复估算，主实验约 1920 份输出。
   第二模型族若按预登记的 40 个问题子集、相同 4 组和 3 次重复运行，另约 480 份输出。
   合计约 2400 次生成，尚不含先导、评估器、额外消融及失败重试；实际预算在 G2 冻结。
6. 消融与鲁棒性覆盖：移除一种证据、关闭重排或引用约束、近似不支持条款、错误版本、
   不可回答及冲突场景。干净样例和扰动配对，避免全拒答得到表面低错误率。
7. 至少两个独立生成模型族验证；检索骨干对照和公开外部基准按实际硬件、接口与标签匹配
   情况运行。公开数据保留官方划分，子集在查看结果前选取，不伪造其没有的法规标签。
8. 只对有明确失败原因的单元重跑，保留第一次失败，不选择性删除不利输出。
验收 G4：
所有预登记运行单元均有成功或明确失败记录；有检索逐问题明细、生成原文、运行元数据、
调用计数及成本。未执行的对照不能在论文中被描述为已经完成。
本阶段的批量运行完成，不等于全部生成论断已经核验通过。

阶段 P5 输出复核与完整实验分析
日期：11 月 9–13 日，5 个工作日。
工作：
1. 从真实输出中预先按模式、问题类型和错误场景分层抽取至少 120 份进行双人独立复核。
   保留抽样概率、权重、各自判断和分歧处理；复核时尽量隐藏方法身份。
2. 核对每项论断的原文支持、公司年度、引用位置、法规版本与时间条件及证据不足处理。
   不将 AI 二次回答写成真人专家认证，统一使用“独立复核”。
3. 自动裁判仅作辅助，在独立复核子集上校准；生成器与裁判分别登记。
4. 统计年报与法规 Recall@k、MRR、nDCG、双源覆盖、论断支持、引用覆盖、无依据论断、
   法规适用性错误及回答覆盖；分别报告适用分母和未知比例。
5. 先聚合同一问题的重复生成，再做按公司等相关单元的配对/聚类统计；报告差值、置信区间、
   效应量及必要的多重比较处理。不能为了通过验收要求指定 p 值或正向提升。
6. 从原始明细生成论文图表，完成错误分类、成功与失败案例、成本与时延分解。
7. 统一所有表格、正文数值与生成脚本，形成实验完整版本。
验收 G5：
正式结果可从冻结原始记录复算；独立复核完成且有真实记录；主要表格、图和统计自洽；
负结果、失败、未知及适用边界均进入分析。预计 11 月 13 日达到“实验跑完并分析完成”。

四 复核人手与计算预算

独立复核是最长的不确定环节之一。问题级证据复核、至少 120 份生成输出核验和分歧处理，
先预留合计约 40–80 人时；P1/P2 根据每题证据数和先导耗时修正。
该估计是人工工作量规划，不表示这些人时已经投入，也不替代实际人员安排。
若仅一位复核人员，须如实改为单人复核，不能宣称双人一致性；原双人验收和排期相应调整。
如需维持既定双人标准而人员暂不可用，可先推进代码、批量输出和写作，其正式核验仍待完成。

计算优先使用 GPU 编码和重排，模型冻结，不默认增加微调。
PDF 解析、BM25、文件读写及当前矩阵检索仍是主机基础运算，不称为完全不使用 CPU。
生成 API 费用由真实模型、token、输出长度和重试决定，未取得实测前不给出固定金额。
跨模型所需第二模型服务、公开数据和附加检索模型若不可用，应在正式运行前登记依赖和替代方案。

五 风险触发与时间调整

1. API 认证或格式问题：优先用小请求定位，预计处理 0.5–1 个工作日；超限时调整并发而非反复全库建库。
2. GPU 显存不足：保持 batch 1，检查长度和内存；任何精度或截断变化都记录为新设置并复核，不回退 CPU 模型推理。
3. 年报 OCR/法规适用信息缺口：优先处理主评测所需页和条款，必要时设未知标签或在冻结前调整范围。
4. 复核或第二模型服务延迟：并行推进已有结果分析和论文非结果章节；受影响的实验不标记完成。
5. 方法质量没有提升：检查实现与数据问题后如实报告，修正论证；不能改标签或挑选有利样本。
6. 超出主排期：使用 11 月 23–27 日缓冲；若仍有外部依赖，列出未完成项和依据重新排期。

六 每次继续工作的记录方式

1. 开始时核对代码/配置、待办清单和最近运行，保留当前修改，不依赖陈旧交接状态。
2. 所有新运行使用独立 run_id，保存输入、配置、模型、原始输出、错误及哈希。
3. 阶段结束写明实际完成、失败原因、验收是否通过、下一步和剩余时间估计。
4. 每周更新一次本计划的实际进度；进度依据产物和验收，不按代码行数或等待时长计算。
5. 若用户要求持续执行，再沿本计划推进；本计划文件本身不创建后台定时任务。
